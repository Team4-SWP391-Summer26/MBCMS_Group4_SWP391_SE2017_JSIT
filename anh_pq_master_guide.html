Cẩm Nang Master Kỹ Thuật & Luồng Chạy Code

Tài liệu trực quan chi tiết từng dòng code, luồng di chuyển dữ liệu từ View (JSP) → Servlet → Service → DAO → Database SQL Server dành cho 5 chức năng phụ trách bởi AnhPQ (Phạm Quốc Anh).

1. Tổng Quan Kiến Trúc MVC & Ánh Xạ Tệp Tin

Hệ thống PentaPlex xây dựng chuẩn mô hình Model-View-Controller (MVC) 4 tầng decoupling trên nền tảng Java Servlet (Jakarta EE) + JSP + JSTL + SQL Server. Luồng dữ liệu hoạt động khép kín theo nguyên tắc:

1
Tầng View (JSP / Form / JavaScript / AJAX)
Người dùng tương tác trên giao diện, bấm nút Submit Form POST hoặc kích hoạt hàm fetch() / AJAX GET/POST gửi dữ liệu về Server.
2
Tầng Controller (HttpServlet / @WebServlet)
Servlet kiểm tra quyền hạn Session (Filter/Role Boundary), đọc tham số req.getParameter(), validate cú pháp đầu vào cơ bản và điều hướng luồng.
3
Tầng Service (Business Logic)
Thực hiện các tính toán phức tạp (tính tiền vé, kiểm tra hạn khuyến mãi, mã hóa OTP, tính tỷ lệ % lấp đầy ghế, xử lý giao dịch Transaction).
4
Tầng Data Access (DAO / PreparedStatement / SQL)
Mở kết nối CSDL via DBContext, thực thi câu lệnh SQL chống SQL Injection bằng PreparedStatement, đọc ResultSet mapping thành đối tượng Java Model.

2. Chuyên Sâu Chức Năng 1: Promotions (Quản Lý & Xác Thực Khuyến Mãi)

Mục tiêu nghiệp vụ
Quản lý chi nhánh (Branch Manager) có thể khởi tạo, sửa đổi, bật/tắt hoặc xóa khuyến mãi dành riêng cho chi nhánh của mình. Khách hàng hoặc nhân viên quầy khi áp mã mua vé sẽ được hệ thống kiểm tra điều kiện khắt khe thời gian thực qua AJAX.

2.1. Chi Tiết Các Thao Tác Nghiệp Vụ & Luồng Code Chạy Từ View → DB

THAO TÁC 1: TẠO MỚI KHUYẾN MÃI (CREATE PROMOTION)

1
JSP View Form Submit
Người dùng nhập các trường vào form.jsp và ấn nút "Save Promotion". Form thực hiện Submit HTTP POST tới URL /branch/promotions/create.
2
Servlet Parsing & Validation (PromotionCreateServlet.java)
Servlet kiểm tra Session currentBranchId. Đọc tham số code, name, discountType, discountValue, minOrderAmount, maxUses, startDate, endDate.
Tất cả Validation Rules được áp dụng:
  • Code: Không được rỗng, tối đa 20 ký tự, regex ^[a-zA-Z0-9]+$.
  • Name: Không rỗng, tối đa 150 ký tự.
  • Discount Type: Phải thuộc PERCENT hoặc FIXED_AMOUNT.
  • Discount Value: Phải > 0. Nếu loại PERCENT thì giá trị phải <= 100%.
  • Min Order Amount: Không được âm (>= 0).
  • Max Uses: Nếu nhập thì phải là số nguyên dương > 0. (Để trống = Vô hạn).
  • Validity Period: valid_to >= valid_from và valid_from >= ngày hiện tại.
  • Uniqueness: Gọi promotionDAO.existsByCode(code) kiểm tra mã chưa tồn tại trong CSDL.
3
DAO Execution & Database Insert (PromotionDAOImpl.java)
Nếu Validation thông qua, gán p.setBranchId(sessionBranchId) để khóa phạm vi chi nhánh. Gọi promotionDAO.insert(p) thực thi SQL INSERT INTO dbo.promotions (...).
4
Asynchronous Background Broadcast & Redirect
Nếu promotion được tạo ở trạng thái Kích hoạt (active = true), Servlet khởi tạo luồng chạy ngầm new Thread(() -> notificationService.broadcastPromotion(saved)).start() để gửi thông báo cho khách hàng mà không làm treo trình duyệt. Sau đó thực hiện PRG Pattern Redirect: resp.sendRedirect("/branch/promotions?created=1").

THAO TÁC 2: CHỈNH SỬA KHUYẾN MÃI (EDIT PROMOTION)

1
GET Request Load Data
Bấm nút Edit tại list.jsp → Gửi GET /branch/promotions/edit?id=X → PromotionEditServlet.doGet() đọc ID, gọi promotionDAO.findById(id) → Kiểm tra bảo mật chi nhánh existing.getBranchId().equals(sessionBranchId) → Bind đối tượng vào Request Attributes → Forward hiển thị trên form.jsp với isEdit = true.
2
POST Request Save Changes
Submit form → PromotionEditServlet.doPost() validate dữ liệu tương tự tạo mới, riêng kiểm tra trùng mã gọi existsByCodeExcludeId(code, promoId) (cho phép giữ nguyên mã của chính nó) → Bảo lưu số lượt đã dùng usedCount cũ → Thực thi promotionDAO.update(p) SQL UPDATE dbo.promotions SET ... WHERE promo_id = ? → Redirect /branch/promotions?updated=1.

THAO TÁC 3: ĐỔI TRẠNG THÁI (TOGGLE) & XÓA KHUYẾN MÃI (DELETE)

Toggle Active (PromotionToggleServlet.java): Submit Form POST → Đọc ID → Kiểm tra quyền chi nhánh → Gọi promotionDAO.toggleActive(id) thực thi SQL XOR bit UPDATE promotions SET active = active ^ 1 WHERE promo_id = ?. Nếu bật từ Tạm dừng → Kích hoạt, tự động kích hoạt luồng phát thông báo ngầm.

Delete Soft Delete (PromotionDeleteServlet.java): Submit Form POST → Đọc ID → Gọi promotionDAO.delete(id). Trước khi xóa, DAO kiểm tra xem mã promoId này đã nằm trong bất kỳ hóa đơn mua vé nào ở bảng dbo.bookings chưa. Nếu đã được sử dụng trong giao dịch → Ném ngoại lệ IN_USE → Servlet bắt lỗi redirect ?error=in_use hiển thị thông báo "Không thể xóa khuyến mãi đã áp dụng trong lịch sử vé". Nếu chưa dùng → Đánh dấu xóa mềm UPDATE promotions SET is_deleted = 1 WHERE promo_id = ? → Redirect ?deleted=1.

2.2. Kiểm Tra Mã Khuyến Mãi Khi Khách Thanh Toán (PromoValidateServlet.java)

Khi khách hàng hoặc nhân viên quầy gõ mã khuyến mãi và bấm "Áp dụng" trên giao diện mua vé, một yêu cầu AJAX GET gửi đến /staff/promo-validate?code=XYZ&subtotal=500000. Servlet xử lý kiểm tra theo đúng 7 bước nghiêm ngặt: 

// Đoạn mã kiểm tra điều kiện mã Promotion trong PromoValidateServlet.java
Promotion promo = promotionDAO.findByCode(code.trim().toUpperCase());

if (promo == null) {
    result.put("valid", false);
    result.put("message", "Mã khuyến mãi không tồn tại.");
} else if (promo.getBranchId() != null && !promo.getBranchId().equals(branchId)) {
    result.put("valid", false);
    result.put("message", "Mã khuyến mãi không áp dụng cho chi nhánh này.");
} else if (!promo.isActive() || !"Active".equals(promo.getStatus())) {
    result.put("valid", false);
    result.put("message", "Mã khuyến mãi ngưng hoạt động hoặc đã hết hạn.");
} else if (promo.getMaxUses() != null && promo.getUsedCount() >= promo.getMaxUses()) {
    result.put("valid", false);
    result.put("message", "Mã khuyến mãi đã hết lượt sử dụng.");
} else if (promo.getMinOrderAmount() != null && subtotal.compareTo(promo.getMinOrderAmount()) < 0) {
    result.put("valid", false);
    result.put("message", "Đơn hàng chưa đạt giá trị tối thiểu (Tối thiểu: " + promo.getMinOrderAmount() + " VNĐ).");
} else {
    // TÍNH TOÁN SỐ TIỀN ĐƯỢC GIẢM
    BigDecimal discount = BigDecimal.ZERO;
    if ("PERCENT".equals(promo.getDiscountType())) {
        discount = subtotal.multiply(promo.getDiscountValue())
                .divide(BigDecimal.valueOf(100), 0, RoundingMode.HALF_UP);
    } else {
        discount = promo.getDiscountValue();
    }
    // Giảm giá không được vượt quá tổng tiền đơn hàng
    if (discount.compareTo(subtotal) > 0) discount = subtotal;

    result.put("valid", true);
    result.put("discountAmount", discount);
    result.put("totalAmount", subtotal.subtract(discount));
}
mapper.writeValue(resp.getWriter(), result); // Trả về JSON cho Client AJAX
❓ Trừ lượt sử dụng (used_count) thể hiện ở đâu và trừ như thế nào?
Trả lời: Lượt sử dụng used_count KHÔNG trừ ngay lúc khách bấm áp dụng mã (tránh trường hợp khách nhập mã xong tắt máy không mua mà mã vẫn bị trừ).
Logic tăng lượt dùng được thực hiện ngay khi giao dịch thanh toán thành công trong Transaction của BookingServiceImpl.java hoặc CounterBookingServlet.java bằng câu lệnh SQL tăng số nguyên nguyên tử:
UPDATE dbo.promotions SET used_count = used_count + 1 WHERE promo_id = ?.
❓ Chỉ số Revenue Impact (Doanh thu đã giảm) tính như thế nào? Admin khác gì Branch Manager?
Trả lời: Chỉ số Revenue Impact trên Dashboard hiển thị tổng số tiền mà rạp đã giảm giá cho khách hàng trong tháng.
Công thức SQL tính toán trong PromotionDAOImpl.getRevenueImpactThisMonth(branchId):
SELECT ISNULL(SUM(b.discount_amount), 0) FROM dbo.bookings b WHERE b.status = 'CONFIRMED' AND MONTH(b.created_at) = MONTH(GETDATE()) AND (@branchId IS NULL OR s.branch_id = @branchId)
Sự khác biệt Admin vs Branch Manager:
  • Admin: Có `branchId = null`, xem được Revenue Impact trên toàn bộ hệ thống các rạp và xem được tất cả khuyến mãi Global + tất cả các chi nhánh.
  • Branch Manager: Có `branchId = session.currentBranchId`, chỉ xem được Revenue Impact riêng của rạp mình quản lý và chỉ có quyền thêm/sửa/xóa các mã gán cho chi nhánh của mình.

3. Chuyên Sâu Chức Năng 2: Forgot Password (Quên Mật Khẩu OTP)

Mô hình Wizard 3 Bước Bảo Mật Khép Kín
Chức năng cho phép khách hàng khôi phục mật khẩu thông qua 3 màn hình tương tác liên tiếp trên cùng một file JSP forgot-password.jsp được điều khiển bởi ForgotPasswordServlet.java.

LUỒNG CHẠY CODE VÀ DỮ LIỆU CỦA WIZARD QUÊN MẬT KHẨU:

1
BƯỚC 1: Nhập Email & Gửi Mã OTP
Khách nhập Email → POST /auth/forgot-password?step=email → Servlet đọc req.getParameter("email") → Kiểm tra Email có tồn tại trong CSDL qua customerDAO.findByEmail(email) → Sinh mã OTP 6 số ngẫu nhiên bằng thuật toán 100000 + random.nextInt(900000) → Lưu các thuộc tính vào Session:
session.setAttribute("forgot_email", email)
session.setAttribute("forgot_otp_expiry", System.currentTimeMillis() + 15 * 60 * 1000) (Hạn 15 phút)
session.setAttribute("forgot_failed_attempts", 0) (Khởi tạo đếm sai)
Gửi Email bất đồng bộ qua emailService.sendOtpEmail(email, otp) → Render giao diện Bước 2 (OTP Entry).
2
BƯỚC 2: Nhập & Xác Thực Mã OTP
Khách nhập mã 6 số → POST /auth/forgot-password?step=verify → Servlet đối chiếu OTP.
Các chốt chặn bảo mật tại Bước 2:
  1. Kiểm tra thời gian (Expiry Check): Nếu System.currentTimeMillis() > expiryTime → Báo lỗi "Mã OTP đã hết hạn (15 phút)".
  2. Kiểm tra giới hạn thử (Brute-force Lockout): Nếu nhập sai, tăng failedAttempts++. Nếu failedAttempts >= 3 → Hủy Session khôi phục, báo lỗi "Bạn đã nhập sai 3 lần. Phiên giao dịch bị khóa để bảo vệ tài khoản" → Đẩy về Bước 1.
  3. Kiểm tra khớp mã: Nếu mã khớp → Đánh dấu session.setAttribute("forgot_otp_verified", true) → Render giao diện Bước 3 (Reset Password).
3
BƯỚC 3: Nhập Mật Khẩu Mới & Cập Nhật CSDL
Khách nhập mật khẩu mới + xác nhận → POST /auth/forgot-password?step=reset → Servlet kiểm tra forgot_otp_verified == true (chống truy cập vọt bước) → Validate độ mạnh mật khẩu (độ dài 8-64 ký tự, có chữ hoa, chữ số) → Mã hóa mật khẩu bằng thuật toán PBKDF2/Salt → Gọi customerDAO.updatePassword(username, newHashedPassword) → Xóa toàn bộ Session `forgot_*` → Redirect về /auth/login?resetSuccess=true.
❓ Tại sao lại lưu OTP trong HTTP Session mà không lưu trong Database? Dùng cái nào tốt hơn?
Trả lời:
- Lưu trong Session: Đơn giản, nhanh chóng, tự động mất đi khi tắt trình duyệt hoặc hết hạn Session. Phù hợp cho luồng khôi phục nhanh ngắn hạn mà không làm tăng tải ghi I/O vào CSDL SQL Server.
- Lưu trong Database: Tốt hơn khi cần hỗ trợ đa thiết bị (khách xin mã trên điện thoại nhưng nhập trên máy tính) hoặc cần lưu lại lịch sử Audit Log chống gian lận. Trong dự án PentaPlex, việc lưu trong Session đảm bảo tốc độ đáp ứng tức thì và bảo mật tốt trên cùng 1 phiên duyệt web.

4. Chuyên Sâu Chức Năng 3: Counter Booking (Đặt Vé Tại Quầy)

Chức năng dành cho nhân viên quầy (CounterBookingServlet.java) phục vụ bán vé trực tiếp cho khách mua tại rạp, tích hợp bán kèm đồ ăn F&B, áp mã giảm giá và xuất hóa đơn thanh toán VNPAY QR hoặc tiền mặt.

CÁC BƯỚC XỬ LÝ TRONG NGHỆP VỤ BÁN VÉ TẠI QUẦY:

  1. Tải sơ đồ suất chiếu AJAX: Nhân viên chọn Phim + Ngày → Trình duyệt gửi AJAX action=getShowtimes → Servlet lọc suất chiếu thuộc chi nhánh qua showtimeDAO.findByMovieAndDate(movieId, date, branchId) trả về JSON danh sách suất chiếu.
  2. Load sơ đồ ghế & Tạm giữ (Soft Lock): Chọn suất chiếu → Lấy danh sách ghế từ seatService.getSeatsByRow(showtimeId). Khi nhân viên click chọn ghế, client gửi tin nhắn WebSocket SELECT tạm giữ ghế trong 10 phút.
  3. Xử lý thông tin Khách hàng (Member vs Walk-in Guest): Hàm resolveCustomerUsername(param) xử lý: Nếu nhân viên để trống hoặc gõ "guest01" → Tự động gán cho tài khoản khách vãng lai guest01. Nếu gõ tên đăng nhập khách thành viên → Tra cứu CSDL qua customerDAO.findByUsername() để tích điểm.
  4. Tính giá vé & Khuyến mãi: Gọi pricingService.calculateTicketPrice() tính phụ thu loại ghế VIP (mặc định +20%) → Gọi PromoValidateServlet tính số tiền giảm giá.
  5. Thanh toán & Chốt ghế (Hard Lock Transaction):
    • Tiền mặt (CASH): Đổi trạng thái Booking thành CONFIRMED, lưu vé booking_seats, trừ kho đồ ăn, gửi sự kiện WebSocket HARD_LOCK và gọi InvoicePdfUtil.java in hóa đơn PDF.
    • VNPAY QR: Tạo URL thanh toán QR via VnPayUtil.createPaymentUrl(). Sau khi khách quét mã thanh toán thành công, VNPAY chuyển hướng về CounterVnPayReturnServlet.java để chốt hóa đơn.

5. Chuyên Sâu Chức Năng 4: F&B Fulfillment (Chế Biến & Trả Đồ Ăn)

Chức năng cho phép nhân viên quầy bắp nước (StaffFoodOrderServlet.java) theo dõi danh sách các đơn đồ ăn của chi nhánh, chuẩn bị món và chuyển đổi trạng thái phục vụ.

Cô Lập Dữ Liệu Chi Nhánh (Branch Isolation) Bảo mật

Servlet bắt buộc kiểm tra Long branchId = session.getAttribute("currentBranchId"). Câu lệnh SQL trong FoodService.getFoodOrdersByBranch(branchId) luôn lọc WHERE branch_id = ?. Nhân viên rạp Nguyễn Huệ tuyệt đối không bao giờ nhìn thấy hoặc can thiệp đơn đồ ăn của rạp Bà Triệu.

Vòng Đời Trạng Thái Đơn Món State Flow

Trạng thái chuyển đổi qua AJAX POST: PENDING (Chờ chế biến) → PREPARING / COOKING (Đang làm bắp/nước) → COMPLETED (Đã giao khách thành công) hoặc CANCELLED (Hủy đơn).

6. Chuyên Sâu Chức Năng 5: Track Occupancy & Monitor Status

Màn hình giám sát trực quan thời gian thực (ShowtimeMonitorServlet.java + monitor.jsp) giúp Quản lý chi nhánh theo dõi sơ đồ ghế và công suất lấp đầy phòng chiếu của từng suất chiếu.

Công thức tính Tỷ lệ lấp đầy phòng chiếu (Occupancy Rate %)
occupancyPct = (seatsSold * 100) / totalCapacity
Trong đó: seatsSold là tổng số ghế đã bán thành công trong DB (bookedSeatIds.size()), totalCapacity là tổng sức chứa của phòng chiếu (ví dụ 80 ghế).

Đồng Bộ Trạng Thái Ghế Thời Gian Thực Qua WebSocket (SeatWebSocketServer.java)

Trang web kết nối tới Server endpoint @ServerEndpoint("/ws/seats"). Mỗi khi có khách hàng chọn ghế hoặc thanh toán thành công, Server đẩy tin nhắn JSON tới toàn bộ các Session đang mở: 

// Cấu trúc Message JSON phát qua WebSocket:
{
  "showtimeId": 105,
  "action": "SELECT",     // SELECT (Tạm giữ), UNSELECT (Nhả ghế), HARD_LOCK (Đã mua thành công)
  "seatId": 42,
  "status": "HELD"
}

7. Phần Hỏi Xoáy Đáp Sâu Bản Chất Code Java & CSDL (Super-Deep Q&A)

Tổng hợp các câu hỏi vặn kỹ bản chất lập trình Object-Oriented, Cấu trúc dữ liệu, Quản lý bộ nhớ và Security mà Hội đồng phản biện SWP391 thường hay xoáy sâu:

❓ CÂU HỎI 1: Phân tích hàm parseSeatIds? Tại sao khai báo List<Long> mà khởi tạo ArrayList<Long>? Tại sao dùng Long (Wrapper) thay vì long (primitive)? Tại sao lấy danh sách ghế đã mua lại dùng Set<Long>?
Phân tích chuyên sâu:

1. Tách chuỗi (String Parsing): Hàm parseSeatIds("1,2,5") sử dụng String.split(",") tách thành mảng chuỗi, sau đó duyệt từng phần tử qua Long.parseLong(str.trim()) để nạp vào danh sách.

2. Nguyên lý Đa Hình (Polymorphism & Programming to Interface):
Khai báo List<Long> list = new ArrayList<>(); tuân thủ nguyên lý thiết kế OO. List là một Interface, còn ArrayList là một lớp triển khai cụ thể. Khai báo theo kiểu Interface giúp mã nguồn linh hoạt, dễ dàng thay đổi cấu trúc dữ liệu bên dưới (ví dụ đổi từ ArrayList sang LinkedList) mà không làm vỡ các hàm gọi phía sau.

3. Wrapper Class (Long) vs Primitive (long):
Java Generics (Collection<T>) chỉ hoạt động với các Đối Tượng (Objects), không hỗ trợ kiểu dữ liệu nguyên thủy (Primitive types như long, int). Do đó bắt buộc phải dùng lớp bọc Long. Java hỗ trợ cơ chế Autoboxing / Unboxing để tự động chuyển đổi giữa long và Long.

4. Tại sao lấy danh sách ghế bookedSeatIds lại dùng Set<Long> thay vì List<Long>?
- Tốc độ tra cứu O(1): Khi vẽ sơ đồ ghế trên JSP, hệ thống phải lặp qua 80 ghế và kiểm tra bookedSeatIds.contains(seatId). Độ phức tạp tra cứu của Set (HashSet) là $O(1)$ (nhờ bảng băm Hash Table). Trong khi tra cứu trên List (ArrayList) tốn độ phức tạp $O(n)$ (phải duyệt từ đầu đến cuối danh sách). Dùng Set giúp trang web hiển thị sơ đồ ghế nhanh gấp hàng chục lần!
❓ CÂU HỎI 2: tại sao tính tiền vé và khuyến mãi phải dùng BigDecimal mà không dùng double hay float?
Trả lời:
Các kiểu số thực nguyên thủy như double và float biểu diễn số theo chuẩn IEEE 754 nhị phân, dẫn đến hiện tượng sai số làm tròn thập phân (floating-point imprecision). Biểu thức đơn giản như 0.1 + 0.2 trong Java bằng 0.30000000000000004.
Trong ứng dụng tài chính và rạp chiếu phim, sai số dù chỉ 1 đồng cũng gây ra lệch sổ sách kế toán. BigDecimal lưu trữ số dưới dạng số nguyên độ dài vô hạn kèm theo tỷ lệ mũ thập phân, đảm bảo tính toán chính xác tuyệt đối 100%. Khi chia phần trăm khuyến mãi, BigDecimal hỗ trợ chế độ làm tròn chuẩn ngân hàng RoundingMode.HALF_UP.
❓ CÂU HỎI 3: PreparedStatement chống tấn công SQL Injection trong các DAO của bạn như thế nào?
Trả lời:
Khi dùng câu lệnh SQL truyền thống ghép chuỗi (String concatenation), kẻ tấn công có thể gõ ' OR '1'='1 làm thay đổi cấu trúc cây truy vấn SQL.
Với PreparedStatement, Database biên dịch trước (Pre-compile) khung câu lệnh SQL chứa các dấu hỏi chấm ? làm tham số. Khi ta gọi ps.setString(1, input), SQL Server đối xử giá trị truyền vào thuần túy là dữ liệu chuỗi (Literal Data) chứ không bao giờ coi đó là lệnh thực thi SQL, triệt tiêu hoàn toàn nguy cơ SQL Injection.
❓ CÂU HỎI 4: HTTP Session và JSESSIONID Cookie hoạt động ra sao? Server biết request là của ai bằng cách nào?
Trả lời:
Do giao thức HTTP là Stateless (không lưu trạng thái giữa các lần truy cập), Tomcat Web Server sử dụng cơ chế Session:
1. Khi người dùng đăng nhập thành công, Server tạo một đối tượng HttpSession trên bộ nhớ RAM và cấp cho nó một chuỗi định danh duy nhất gọi là JSESSIONID (ví dụ: A1B2C3D4...).
2. Server gửi chuỗi này về trình duyệt lưu dưới dạng một Set-Cookie: JSESSIONID=A1B2C3D4; HttpOnly.
3. Ở các request tiếp theo, trình duyệt tự động đính kèm Cookie này lên Server. Server dựa vào `JSESSIONID` tra cứu vào HashMap quản lý Session để lấy đúng thông tin currentUser và currentBranchId.
❓ CÂU HỎI 5: Tại sao luồng phát thông báo Promotion mới lại tạo Thread riêng (new Thread(...).start())?
Trả lời:
Đây là kỹ thuật Xử lý Bất Đồng Bộ (Asynchronous Processing). Quá trình gửi email/thông báo thông qua mạng Internet có thể mất từ 2 - 5 giây. Nếu gọi trực tiếp trên Thread của Servlet, người dùng bấm "Tạo Khuyến Mãi" sẽ phải chờ 5 giây màn hình mới load xong (nguy cơ Timeout).
Bằng cách đẩy công việc gửi thông báo sang một Thread chạy ngầm riêng biệt, Servlet có thể giải phóng bộ nhớ và trả về câu lệnh Redirect cho trình duyệt ngay lập tức (chỉ mất 50ms), nâng cao trải nghiệm người dùng mượt mà.
